2. Runtime flows

2.1 Sign-up flow (first-time user)

sequenceDiagram
    autonumber
    participant U as User browser
    participant CF as CloudFront
    participant BFF as Lambda BFF
    participant CG as Cognito User Pool
    participant G as Google OAuth
    participant PCT as Post-Confirmation Lambda
    participant DB as Aurora (users table)

    U->>CF: GET / (loads SPA)
    U->>CF: Click "Login with Google"
    CF->>BFF: GET /api/auth/login
    BFF-->>U: 302 redirect to Cognito hosted UI (with state + PKCE)
    U->>CG: GET /oauth2/authorize
    CG-->>U: 302 redirect to Google OAuth
    U->>G: Sign in with Google
    G-->>U: 302 redirect to Cognito with code
    U->>CG: GET /oauth2/idpresponse?code=...
    CG->>PCT: Invoke Post-Confirmation trigger (new user)
    PCT->>DB: INSERT users (cognito_sub, email) RETURNING id
    DB-->>PCT: OK (new row)
    CG-->>U: 302 redirect to /api/auth/callback?code=...&state=...
    U->>CF: GET /api/auth/callback?code=...
    CF->>BFF: forwarded
    BFF->>CG: POST /oauth2/token (code exchange)
    CG-->>BFF: access_token, refresh_token, id_token
    BFF->>DB: INSERT users ... ON CONFLICT (cognito_sub) DO NOTHING (defensive UPSERT)
    DB-->>BFF: no-op (row already exists from trigger)
    BFF-->>U: 302 to /app with Set-Cookie: access_token, refresh_token (HttpOnly, Secure, SameSite=Lax)
    U->>CF: GET /app (cookies attached automatically on next request)
Sign-up flow. The Post-Confirmation trigger creates the row; the BFF defensive UPSERT is a fallback if the trigger ever fails.

2.2 Sign-in flow (returning user)

sequenceDiagram
    autonumber
    participant U as User browser
    participant CF as CloudFront
    participant BFF as Lambda BFF
    participant CG as Cognito User Pool
    participant G as Google OAuth
    participant DB as Aurora

    U->>CF: Click "Login with Google"
    CF->>BFF: GET /api/auth/login
    BFF-->>U: 302 to Cognito hosted UI
    U->>CG: /oauth2/authorize
    CG-->>U: 302 to Google
    U->>G: Sign-in (or silent SSO if Google session active)
    G-->>U: 302 back to Cognito with code
    U->>CG: /oauth2/idpresponse
    Note right of CG: Existing user — same sub.
Post-Confirmation does NOT fire.
    CG-->>U: 302 to /api/auth/callback?code=...
    U->>CF: GET /api/auth/callback
    CF->>BFF: forwarded
    BFF->>CG: token exchange
    CG-->>BFF: tokens
    BFF->>DB: INSERT ... ON CONFLICT DO NOTHING (defensive UPSERT no-ops)
    BFF-->>U: 302 to /app with fresh Set-Cookie pair
Sign-in flow for a returning user. Cognito recognises the existing identity by Google sub, returns the same Cognito sub, no trigger fires. The BFF defensive UPSERT is a safe no-op.

2.3 Streaming chat request

sequenceDiagram
    autonumber
    participant U as User browser
    participant CF as CloudFront
    participant ALB as ALB
    participant API as FastAPI on ECS
    participant DB as Aurora
    participant BR as Bedrock

    U->>CF: POST /api/v1/chat/stream (cookie: access_token=...)
    CF->>ALB: forwarded (Cookie header passed via Managed-AllViewer)
    ALB->>API: HTTP request
    API->>API: SessionPort: verify JWT against Cognito JWKS
    API->>DB: SELECT id FROM users WHERE cognito_sub=$1 (or in-process LRU hit)
    DB-->>API: user_id
    API->>DB: try_advisory_xact_lock(hash(conversation_id))
    DB-->>API: acquired
    API->>DB: load conversation messages
    API->>BR: streaming inference call (with prompt cache_control)
    loop SSE token stream
        BR-->>API: text delta
        API-->>ALB: SSE frame (text/event-stream)
        ALB-->>CF: passthrough
        CF-->>U: SSE frame
    end
    API->>DB: persist assistant message + usage
    API-->>U: finish event
Streaming chat with HTTPOnly cookie auth, JWKS-cached JWT validation, Postgres advisory lock for per-conversation serialisation, and SSE passthrough via CloudFront.

2.4 Aurora cold-start scenario

sequenceDiagram
    autonumber
    participant U as User browser
    participant SPA as SPA
    participant API as FastAPI
    participant DB as Aurora (paused)

    Note over DB: Idle > 5min → paused at 0 ACU.
If > 24h since last query, "deep sleep".
    U->>SPA: Open https://app.convfinqa...
    SPA->>API: GET /api/v1/healthz (warm-up fetch on mount)
    Note over SPA: Loader: "Waking up infrastructure..."
    API->>DB: SELECT 1
    DB->>DB: resume (15s short, 30s+ deep sleep)
    DB-->>API: OK
    API-->>SPA: 200
    SPA-->>U: hide loader, render app
    U->>SPA: type message, click Send
    SPA->>API: POST /api/v1/chat/stream
    Note over API,DB: Connection pool now warm → no delay.
    API->>DB: queries
    DB-->>API: ms-level
    API-->>U: streaming response
Aurora wake-up flow. The SPA fires a warm-up fetch on mount so the cold-start hits the loader, not the user's first interaction.
